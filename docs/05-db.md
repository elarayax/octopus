# `db.go` — Persistencia en SQLite

~470 líneas. Guarda lo que debe sobrevivir a un reinicio: canales, mensajes,
directorio de miembros y preferencias. También define el esquema y las
migraciones.

## El esquema (`schema.sql`)

| Tabla | Para qué |
|-------|----------|
| `usuario` | nombres de quienes han escrito (se crea sola al guardar un mensaje) |
| `servidor` | tabla legacy (quedó del diseño con servidores locales) |
| `tipo_canal` | tipos de canal (legacy) |
| `canal` | **los canales**: código, nombre, subtítulo, ícono |
| `usuarios_servidor` | relación legacy |
| `mensaje` | **los mensajes**: contenido, tipo, canal, autor, fecha |
| `foro_post` / `foro_comentario` | legacy (no se usan) |
| `miembro` | **el directorio**: código → nombre + avatar |
| `configuracion` | preferencias clave/valor (username, volúmenes) |

**Por qué tres tablas seemingly redundantes** (`usuario`, `miembro`,
`onlineSet`): cada una resuelve un problema distinto.

| Dónde | Qué guarda | Ciclo de vida |
|-------|-----------|--------------|
| `usuario` | nombres vistos en mensajes | permanente |
| `miembro` | código + nombre + avatar | permanente (es el directorio) |
| `onlineSet` (memoria) | quién está conectado **ahora** | efímero |

El directorio es permanente (para reconocer a un amigo desconectado), pero
la presencia no puede serlo (cambia con el tiempo).

## `initDB() error`

La función que abre la base y la deja lista.

### Abrir con un DSN preparado

```go
dbPath := filepath.Join(configDir, "app_data.db")

dsn := fmt.Sprintf("%s?_busy_timeout=5000&_pragma=journal_mode(WAL)"+
    "&_pragma=synchronous(NORMAL)&_pragma=foreign_keys(1)", dbPath)

db, err := sql.Open("sqlite", dsn)
```

**Por qué un DSN con parámetros y no `sql.Open("sqlite", dbPath)`**:

- **`busy_timeout=5000`**: sin él, SQLite **falla al instante** con
  `database is locked (SQLITE_BUSY)` cuando hay contención. Con él, espera
  hasta 5 segundos. Es el fix del error que te salía.
- **`journal_mode=WAL`**: en WAL, los lectores no bloquean al escritor. Antes
  (modo `DELETE`), una lectura abierta impedía la escritura.
- **`foreign_keys(1)`**: se aplica en **cada conexión** del pool. Antes se
  ejecutaba un `PRAGMA foreign_keys = ON` suelto, que solo afectaba a **una**
  de las conexiones del pool → las claves foráneas no se aplicaban en el
  resto.
- **`synchronous(NORMAL)`**: con WAL es seguro y noticeably más rápido.

Detalle técnico: el driver `modernc.org/sqlite` aplica los parámetros del DSN
**en cada conexión nueva** (en su "apply phase"), que es exactamente lo que
hace falta. Por eso van en el DSN y no como un `db.Exec` suelto.

> **Por qué NO usar `SetMaxOpenConns(1)`**: funcionaría (serializa todo), pero
> introduce un **deadlock latente**: si algún día alguien escribe una query
> dentro de un `rows.Next()` abierto, la escritura espera la conexión que el
> lector tiene ocupada, y el lector espera a la escritura. Con WAL + busy
> timeout no hay ese riesgo.

### Migración 1 — la tabla `canal` sin columna `codigo`

```go
if canalExists && !hasCodigo {
    db.SetMaxOpenConns(1)              // ← una sola conexión durante el DDL
    db.Exec("PRAGMA foreign_keys = OFF;")
    db.Exec(`CREATE TABLE IF NOT EXISTS canal_new (...)`)
    db.Exec(`INSERT OR IGNORE INTO canal_new (id, codigo, nombre)
              SELECT id, CASE WHEN id = 1 THEN 'LOCAL' ELSE printf('C%05d', id) END, ...`)
    db.Exec("DROP TABLE canal;")
    db.Exec("ALTER TABLE canal_new RENAME TO canal;")
    db.Exec("PRAGMA foreign_keys = ON;")
    db.SetMaxOpenConns(0)              // ← restaurar el pool
}
```

**Por qué el dance de `canal_new`**: SQLite (en las versiones usadas) no
permite añadir una columna `NOT NULL UNIQUE` a una tabla con `ALTER TABLE`.
La solución es crear una tabla nueva, copiar los datos, borrar la vieja y
renombrar.

**Por qué `CASE WHEN id = 1 THEN 'LOCAL' ELSE printf('C%05d', id)`**: el canal
local (id 1) conserva un código legible; los demás reciben un código
sintético único.

**Por qué `SetMaxOpenConns(1)` durante la migración**: los `PRAGMA
foreign_keys` son **por conexión**. Con el pool normal, el `OFF` y el `ON`
podrían aplicarse a conexiones distintas y la migración fallaría. Forzando una
sola conexión se garantiza la coherencia.

### Migración 2 — columna `tipo` en `mensaje`

```go
db.Exec(`ALTER TABLE mensaje ADD COLUMN tipo VARCHAR(10) NOT NULL DEFAULT 'text'`)
```

**Por qué el default**: los mensajes existentes son texto. Se ignoran los
errores ("duplicate column name") por si ya se migró.

### Migración 3 — el canal por defecto

```go
db.Exec(`INSERT INTO canal (id, codigo, nombre) VALUES (1, 'LOCAL', 'Canal local')
         ON CONFLICT(codigo) DO NOTHING`)
```

**Por qué `ON CONFLICT DO NOTHING`**: es idempotente. Se puede ejecutar en
cada arranque sin duplicar filas.

### Restaurar el canal activo

```go
db.QueryRow(`SELECT id FROM canal ORDER BY ultima_vez DESC LIMIT 1`).Scan(&lastCanalID)
```

**Por qué**: al reabrir la app se vuelve al último canal usado. `ultima_vez`
se actualiza con `CURRENT_TIMESTAMP` en cada `upsertCanal`.

## Preferencias: `saveSetting` / `getSetting`

```go
func (a *App) saveSetting(clave, valor string) {
    if a.db == nil { return }
    db.Exec(`INSERT INTO configuracion (clave, valor) VALUES (?, ?)
             ON CONFLICT(clave) DO UPDATE SET valor = excluded.valor`, clave, valor)
}
```

**Por qué `excluded.valor`**: es la forma estándar de "en el ON CONFLICT, usa
el valor que se intentó insertar".

**Por qué el `if a.db == nil`**: los métodos se pueden llamar antes de
`startup` (o en tests). Es una guarda defensiva.

## El directorio: `Miembro`, `upsertMiembro`, `getMiembros`

```go
type Miembro struct {
    Codigo string `json:"codigo"`
    Nombre string `json:"nombre"`
    Avatar string `json:"avatar"` // base64 del WebP (estático o animado)
}
```

### `upsertMiembro(codigo, nombre, avatarB64 string)`

```go
if avatarB64 != "" {
    db.Exec(`INSERT INTO miembro (codigo, nombre, avatar) VALUES (?, ?, ?)
             ON CONFLICT(codigo) DO UPDATE SET nombre = excluded.nombre,
             avatar = excluded.avatar, ultima_vez = CURRENT_TIMESTAMP`)
} else {
    db.Exec(`INSERT INTO miembro (codigo, nombre) VALUES (?, ?)
             ON CONFLICT(codigo) DO UPDATE SET nombre = excluded.nombre,
             ultima_vez = CURRENT_TIMESTAMP`)
}
```

**Por qué hay dos queries**: si el avatar viene vacío, **no** se debe borrar
el que ya estaba. Un solo `INSERT ... ON CONFLICT` sobrescribiría el avatar
con "" y el usuario perdería su foto cada vez que alguien se presenta sin
imagen.

**Por qué `ultima_vez`**: para ordenar el directorio por "visto recientemente"
y para saber quién es el más antiguo.

### `getMiembros() []Miembro`

```go
db.Query(`SELECT codigo, nombre, COALESCE(avatar, '') FROM miembro
          ORDER BY ultima_vez DESC`)
```

**Por qué `COALESCE`**: la columna puede ser NULL en bases antiguas; `COALESCE`
lo convierte en "" y evita que `Scan` falle con un error de tipo.

**Por qué `ORDER BY ultima_vez DESC`**: los miembros recientes primero.

## Los canales

### `upsertCanal(codigo, nombre, subtitulo, icono string) int`

```go
db.QueryRow(`
    INSERT INTO canal (codigo, nombre, subtitulo, icono) VALUES (?, ?, ?, ?)
    ON CONFLICT(codigo) DO UPDATE SET ultima_vez = CURRENT_TIMESTAMP
    RETURNING id
`).Scan(&id)
```

**Por qué `RETURNING id`**: evita el patrón "INSERT y luego SELECT para
obtener el id". `RETURNING` (SQLite 3.35+) devuelve el id generado en la
misma sentencia. **Una sola operación atómica** → menos contención.

**Por qué el `ON CONFLICT` solo actualiza `ultima_vez`**: al hacer upsert de
un canal no se quiere pisar su nombre/ícono personalizado con los valores por
defecto. El `nombre` del canal lo gestiona el anfitrión y se propaga por el
paquete `channel`.

**El fallback**:
```go
if id == 0 {
    db.QueryRow(`SELECT id FROM canal WHERE codigo = ?`).Scan(&id)
    if id == 0 {
        fmt.Printf("upsertCanal fallback failed for codigo=%s\n", codigo)
        return a.currentChannelID
    }
}
```

**Por qué un fallback**: si el `RETURNING` falla por un motivo raro, se
intenta un SELECT. Si tampoco funciona, se devuelve el canal actual en vez de
0 (un id 0 haría que la app no guardara nada).

### `updateCanalInfo(id, nombre, subtitulo, icono)`

`UPDATE` simple. Guarda la identidad del canal.

### `getCanalByCodigo(codigo) (ChannelInfo, int)`

`SELECT` por código. Si no existe, devuelve los valores por defecto y `id = 0`
(para que el llamante sepa que debe crearlo).

### `GetCanales() []CanalEntry`

```go
type CanalEntry struct {
    Codigo    string `json:"codigo"`
    Nombre    string `json:"nombre"`
    Subtitulo string `json:"subtitulo"`
    Icono     string `json:"icono"`
    UltimaVez string `json:"ultimaVez"`
}
```

**Por qué `UltimaVez` como string**: SQLite devuelve el timestamp formateado
por `CURRENT_TIMESTAMP` ("YYYY-MM-DD HH:MM:SS", en UTC). Es más simple que
parsearlo a `time.Time` para mostrarlo en la UI.

## Los mensajes

### `saveMessageKind(sender, contenido, kind, creadoEn string)`

```go
db.Exec(`INSERT OR IGNORE INTO usuario (id, nombre) VALUES (?, ?)`, sender, sender)
if creadoEn != "" {
    db.Exec(`INSERT INTO mensaje (contenido, tipo, id_canal, id_usuario, creado_en)
              VALUES (?, ?, ?, ?, ?)`, ...)
} else {
    db.Exec(`INSERT INTO mensaje (contenido, tipo, id_canal, id_usuario)
              VALUES (?, ?, ?, ?)`, ...)
}
```

**Por qué `INSERT OR IGNORE INTO usuario`**: el autor del mensaje debe existir
en `usuario` por la clave foránea. `OR IGNORE` evita el error si ya existe.

**Por qué el `creadoEn` es opcional**: al **fusionar** un historial remoto, el
mensaje conserva su fecha original (para que el orden cronológico sea
correcto entre equipos). Un mensaje nuevo usa `CURRENT_TIMESTAMP`.

**Por qué el `kind`**: distingue "text" de "image". La columna `tipo` es
además una migración (ver arriba).

### `messageExists(sender, contenido, creadoEn string) bool`

```go
db.QueryRow(`SELECT COUNT(*) FROM mensaje WHERE id_canal = ? AND id_usuario = ?
             AND contenido = ? AND strftime('%Y-%M-%D %H:%M:%S', creado_en) = ?`,
            canal, sender, contenido, creadoEn).Scan(&n)
```

**Por qué compara el timestamp con `strftime`**: el timestamp se guardó como
texto. `strftime` normaliza ambos a formato "YYYY-MM-DD HH:MM:SS" para
comparar correctamente (evita que "2026-10-21 01:24:24" != "2026-10-21
01:24:24" por diferencias de formato).

**Para qué sirve**: deduplicar la fusión de historiales. Sin esto, cada peer
recibiría duplicados de los mensajes que ya tenía.

### `GetChatHistory() []Message`

```go
db.Query(`SELECT id_usuario, contenido, tipo, strftime('%Y-%m-%d %H:%M:%S', creado_en)
          FROM mensaje WHERE id_canal = ? ORDER BY creado_en ASC, id ASC`)
```

**Por qué `ORDER BY creado_en ASC, id ASC`**: cronológico, y el `id` desempata
los mensajes del mismo segundo (determinismo).

**Por qué el `strftime` en el SELECT**: devuelve el timestamp ya formateado
para la UI, sin parsear en Go.

### `historyBudget` y `exportHistory() string`

```go
const historyBudget = 1500 * 1024  // 1.5 MB
```

```go
rows, _ := db.Query(`SELECT id_usuario, contenido, tipo, creado_en FROM mensaje
                     WHERE id_canal = ? ORDER BY creado_en DESC LIMIT 500`)
```

**El algoritmo**:

1. Toma los **500 mensajes más recientes** (`DESC` + `LIMIT`: es lo más
   eficiente con índice).
2. Va acumulando el tamaño estimado (`size + 60` por mensaje: JSON + campos).
3. Cuando supera el presupuesto, **para** (`break`).
4. **Invierte** el slice para devolverlos en orden cronológico.

**Por qué invertir al final**: es más eficiente pedir los recientes en DESC
que ordenar ascendentemente toda la tabla, y el resultado final es el mismo.

**Por qué 1.5 MB**: el tope de SCTP son 4 MB (configurado en
`newPeerConnection`). El historial ocupa ~1.5 MB para dejar aire a imágenes
(400 KB) y avatares (300 KB) en el mismo mensaje.

**Por qué el JSON con la forma `{sender, body, kind, time}`**: es un formato
ligero y explícito para la fusión (distinto del `Packet` de la app, más
orientado a datos que a mensajes).

### `mergeHistory(historyJSON string) int`

```go
for _, m := range msgs {
    if m.Sender == "" || m.Time == "" { continue }
    if m.Kind != "image" { m.Kind = "text" }
    if a.messageExists(m.Sender, m.Body, m.Time) { continue }
    a.saveMessageKind(m.Sender, m.Body, m.Kind, m.Time)
    added++
}
return added
```

**Por qué normalizar `kind`**: los histories antiguos no tenían el campo.
Sin normalizar, un mensaje sin `kind` se guardaría con `kind = ""` y la UI no
lo renderizaría bien.

**Por qué devolver el número de añadidos**: la UI emite `history_synced` con
ese dato para informar ("se sincronizaron N mensajes").

## Resumen de las decisiones de diseño de la BD

| Decisión | Motivo |
|----------|--------|
| DSN con `busy_timeout` + WAL | evitar `SQLITE_BUSY` |
| Pragmas en el DSN (no `Exec` suelto) | se aplican a **cada** conexión del pool |
| `RETURNING id` | obtener el id sin una segunda consulta |
| `upsertCanal` no pisa nombre/ícono | la identidad la gestiona el anfitrión |
| `upsertMiembro` con dos queries | no borrar el avatar si viene vacío |
| `messageExists` con `strftime` | deduplicar la fusión de historiales |
| `historyBudget` de 1.5 MB | dejar aire en el tope SCTP de 4 MB |
| Migración con tabla `canal_new` | SQLite no permite `ALTER TABLE ADD COLUMN ... UNIQUE NOT NULL` |
